# Wiki Tags Vertical Slice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Admin edits optional tags on drafts and publishes an immutable tag snapshot; website and Flutter can discover and filter only published tags.

**Architecture:** Persist independent tags, draft-tag and revision-tag join tables with restrictive FKs and unique normalized name/slug keys. Validate and change draft-tag membership inside existing serializable article mutations; create revision-tag rows atomically on publication. Public API joins the current published revision, never draft membership, and returns tag metadata to both clients.

**Tech Stack:** .NET 10 / EF Core SQL Server, Next.js TypeScript, Flutter, Node 22 native test runner, xUnit (requires SDK).

**Spec:** `openspec/changes/add-wiki-cms/specs/wiki-content/spec.md`; architecture `docs/superpowers/specs/2026-09-17-nova-haven-platform-design.md`.

## Global Constraints

- Maximum 10 distinct active tag UUIDs per draft, malformed/duplicate IDs return validation 400. No tags is valid.
- Historical revision tags remain immutable; tag rename, slug change, deactivate and delete are disallowed while any draft/history references exist; no cascade-delete history.
- Admin requires role + CSRF and If-Match on tag PATCH/DELETE and article updates. All reference checks and writes execute inside serializable transaction; deadlocks map to 409.
- Public list/detail/filter/tag catalog depend only on currently published revision; never draft. Keep original published version stable across draft edits/restore.
- No claim of .NET, Flutter or SQL build/test without running corresponding SDK/integration checks.
